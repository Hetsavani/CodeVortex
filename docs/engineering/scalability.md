# Distributed Systems & Scalability Design

## Current Scalability Situation

The current system has a single Express server with no concurrency management. Code execution blocks the event loop while waiting for child processes. There's no queue, no worker pool, no horizontal scaling. One busy user can degrade the experience for everyone.

This document evaluates which distributed-system concepts genuinely help at each scale stage, and which would be premature.

---

## Concept-by-Concept Evaluation

---

### 1. Job Queue for Code Execution

**Problem it solves**: Without a queue, the API server is both the request handler and the execution engine. If many users run code simultaneously, the server is overwhelmed. A slow execution blocks others.

**Why this project needs it**: Code execution is CPU-intensive and variable-duration. It shouldn't compete with fast API requests (file saves, tree fetches) for server resources.

**Recommended implementation**:
Use a Redis-backed queue (`bull` or `bullmq` — both battle-tested Node.js queue libraries).

```
API Server          Redis Queue          Worker Process
    │                    │                    │
    │  enqueue job ──▶  │                    │
    │                    │  dequeue job  ──▶  │
    │                    │                    │  spawn Docker container
    │                    │                    │  stream output via Socket.IO
    │                    │  complete ──────────│
```

The worker can run as a separate Node.js process on the same machine, or on a dedicated VM if execution load grows.

**Complexity**: Medium  
**Priority**: Phase 2 (after Docker sandboxing is working) — start with direct Docker calls from API server, then extract to queue/worker when needed.

---

### 2. Worker Pool

**Problem it solves**: Limits concurrent executions to prevent resource exhaustion. Without this, 100 simultaneous users each running a CPU-heavy program would saturate the server.

**Why this project needs it**: Even with Docker isolation, the host machine has finite CPU/memory. A worker pool enforces concurrency limits.

**Recommended implementation**:
BullMQ has a built-in concurrency setting:

```javascript
const worker = new Worker('execution', processJob, {
  connection: redis,
  concurrency: 5  // Max 5 simultaneous executions per worker
});
```

For a single worker process on a 2-core server, `concurrency: 4` is a reasonable starting point.

**Complexity**: Low (once queue is in place)  
**Priority**: Phase 2, alongside the queue.

---

### 3. Backpressure

**Problem it solves**: When the queue fills up faster than workers can process jobs, new requests should receive a meaningful response ("Server busy, try again soon") instead of silently queuing indefinitely.

**Why this project needs it**: Without backpressure, users submitting code during a busy period would wait indefinitely with no feedback.

**Recommended implementation**:
Check queue depth before accepting new jobs:

```javascript
const queueSize = await executionQueue.count();
if (queueSize > 100) {  // configurable threshold
  return res.status(429).json({ 
    error: 'Server busy', 
    retryAfter: 30 
  });
}
```

**Complexity**: Low  
**Priority**: Phase 2, alongside the queue.

---

### 4. Rate Limiting

**Problem it solves**: Prevents any single user from monopolizing execution resources, abusing the AI API, or brute-forcing auth.

**Why this project needs it**: Currently there is no rate limiting at all. This is both a security and scalability problem.

**Recommended implementation**:

**Tier 1 — Per-IP (express-rate-limit, in-memory)**:
```javascript
import rateLimit from 'express-rate-limit';

const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,  // 15 minutes
  limit: 10,                   // 10 attempts per window per IP
  message: 'Too many login attempts'
});

app.use('/api/auth', authLimiter);
```

**Tier 2 — Per-User (Redis-backed)**:
```javascript
// For execution and AI endpoints:
// Max 30 executions per hour per user
const key = `rate:exec:${userId}:${hourBucket}`;
const count = await redis.incr(key);
await redis.expire(key, 3600);
if (count > 30) {
  return res.status(429).json({ error: 'Hourly execution limit reached' });
}
```

**Complexity**: Low  
**Priority**: Phase 1 (security critical — implement immediately).

---

### 5. Idempotency

**Problem it solves**: If a client retries a request (network timeout, browser refresh), the server should not run the same code twice.

**Why this project needs it**: A user clicking "Run" twice in quick succession should not spawn two containers. More importantly, if the response is lost in transit, a retry should return the original result.

**Recommended implementation**:
Accept an optional `idempotencyKey` from the client (UUID generated by the browser before submitting). Check Redis before starting execution:

```javascript
const existing = await redis.get(`idem:${idempotencyKey}`);
if (existing) {
  return res.json(JSON.parse(existing));  // Return cached result
}
// ... run execution ...
await redis.setex(`idem:${idempotencyKey}`, 300, JSON.stringify(result)); // 5min TTL
```

**Complexity**: Low  
**Priority**: Phase 3.

---

### 6. Horizontal Scaling (Multiple API Servers)

**Problem it solves**: When a single API server is the bottleneck (too much traffic, too many WebSocket connections).

**Why this project needs it**: At current scale, it doesn't. A single server can handle hundreds of concurrent users easily for this type of workload.

**What's required to support it**:
1. All session state must be in Redis (not in-process memory)
2. Socket.IO must use the Redis adapter (`socket.io-redis`) so that events are shared across instances
3. A load balancer (nginx or cloud-managed) must use sticky sessions for WebSocket connections, or the Redis adapter eliminates this requirement

**When to implement**: Only when server CPU or memory becomes the bottleneck, which requires significant traffic. Don't build this prematurely.

**Complexity**: Medium  
**Priority**: Phase 5+ (only when actually needed).

---

### 7. Dead-Letter Queue

**Problem it solves**: Jobs that fail repeatedly (crashed container, out-of-memory during spawn) should be removed from the active queue and stored separately for inspection, not retried infinitely.

**Why this project needs it**: Without this, a consistently failing job (e.g., "run malformed binary") would clog the queue with retries.

**Recommended implementation**:
BullMQ handles this automatically:
```javascript
const job = await executionQueue.add('run', data, {
  attempts: 2,                    // Max 2 attempts
  backoff: { type: 'fixed', delay: 2000 },  // Wait 2s between retries
});

// Failed jobs are moved to the 'failed' set automatically
// Inspect with: await executionQueue.getFailed()
```

**Complexity**: Low (built into BullMQ)  
**Priority**: Phase 2.

---

### 8. Caching (Redis)

**Problem it solves**: Reduces redundant database queries and speeds up common reads.

**What to cache**:

| Data | Cache key | TTL | Reason |
|---|---|---|---|
| Auth token validation | `auth:token:{hash}` | 5 minutes | Avoids DB hit on every request |
| User rate limit counters | `rate:{userId}:{endpoint}:{bucket}` | Match window | Atomic per-user counting |
| Active execution state | `process:{id}` | 30 minutes | Fast lookup without DB query |
| Terminal sessions | `terminal:{id}` | 2 hours | Session persistence |
| Output buffer | `process:buffer:{id}` (list) | 1 hour | Reconnect replay |

**What NOT to cache**:
- File content (stale risk on every save)
- User profile (rarely needed, consistency risk)
- Full file tree (too dynamic)

**Complexity**: Low  
**Priority**: Phase 1 (rate limiting), Phase 2 (execution state).

---

### 9. Distributed Tracing

**Problem it solves**: When a request touches multiple services (API → Redis → Docker → Database), tracing shows which component is slow and where errors occur.

**Why this project needs it**: At the current architecture (one server, one database), request-level timing logs are sufficient. Distributed tracing becomes valuable when there are at least 2–3 services communicating.

**Recommended approach**:
Start with request-level timing logs:
```javascript
const start = Date.now();
const result = await executionService.run(job);
logger.info({ duration: Date.now() - start, executionId }, 'execution complete');
```

Add OpenTelemetry instrumentation when extraction into a queue/worker architecture happens. Using OpenTelemetry from the start is low-cost and high value:
```bash
npm install @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node
```

**Complexity**: Low (setup) to Medium (multi-service tracing)  
**Priority**: Phase 3 (add OTel instrumentation alongside observability work).

---

### 10. Autoscaling

**Problem it solves**: Automatically adding more worker capacity during peak usage and scaling down during low usage.

**Why this project needs it**: At current scale, it doesn't. Autoscaling makes sense only when execution load is variable and measurable.

**When to implement**:
- When on a cloud provider (AWS, GCP, Azure)
- When you have metrics showing clear peak/trough patterns
- When the cost of idle capacity is significant

**Simple implementation when ready**:
Use Docker Swarm or cloud-managed instance groups to run multiple worker processes. The queue (Redis/BullMQ) naturally distributes work across workers.

**Complexity**: High  
**Priority**: Phase 5+ (not needed for 1-2 developer scale).

## Summary: What to Build and When

```
Phase 1 (Immediate):
  ✓ Rate limiting (express-rate-limit + Redis counters)
  ✓ Redis (for rate limiting and execution state)

Phase 2 (After sandbox works):
  ✓ BullMQ job queue for execution
  ✓ Worker concurrency limits (max 5 simultaneous)
  ✓ Dead-letter queue (free with BullMQ)
  ✓ Backpressure (check queue depth)

Phase 3 (After real-time is working):
  ✓ Idempotency keys for execution
  ✓ OpenTelemetry instrumentation

Phase 4+ (Only if scale requires):
  ✗ Horizontal API scaling (needs socket.io-redis adapter)
  ✗ Autoscaling workers
  ✗ Separate worker VM
```

## What NOT to Build (and Why)

**Apache Kafka**: Overkill. Kafka solves problems of massive throughput (millions of events/second) and complex event streaming topologies. A Redis-backed BullMQ queue handles this workload perfectly. Adding Kafka would require operational expertise (ZooKeeper/KRaft, partition management, consumer groups) with zero benefit at this scale.

**Complex distributed scheduling**: A simple queue with priority and concurrency limits is sufficient. Sophisticated scheduling algorithms (fair queuing across users, bin packing) are unnecessary until there are thousands of concurrent users.

**Separate microservices for each language runtime**: Having a separate Python execution service, Node execution service, Java execution service is premature decomposition. A single execution worker that calls Docker with the appropriate image handles this cleanly. Microservices add network hops and deployment complexity for no benefit here.
